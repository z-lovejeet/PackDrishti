## 1. Security Objectives and Statutory Legal Framework

### 1.1 Executive Summary
MetroScan operates at the intersection of public consumer empowerment and statutory legal enforcement. The system processes photographic evidence of packaged retail commodities, performs automated compliance audits against the Legal Metrology (Packaged Commodities) Rules, 2011, and generates legally actionable inspection dockets (FORM LM-INSP-2011) and show-cause notices.

Because inspection reports generated by MetroScan may be produced as primary electronic evidence before Judicial Magistrates, Consumer Disputes Redressal Commissions (District, State, and National), and Metrology Appellate Tribunals, the security posture of the platform must satisfy the most rigorous standards of data integrity, non-repudiation, tamper-evidence, and role-based privilege isolation.

### 1.2 Core Security Objectives
The MetroScan security architecture is founded upon five foundational objectives:

1. **Evidentiary Integrity and Tamper Evidence**:
   Every packaging image ingested by the platform must be cryptographically hashed at the instant of receipt. The system must guarantee that evidence presented in legal notices or court proceedings is mathematically identical to the file captured in the field, preserving an unbroken chain of custody.
2. **Strict Principle of Least Privilege (PoLP)**:
   Access to statutory inspection workflows, manufacturer compliance violation ledgers, officer dispatch coordinates, and formal enforcement dockets is strictly reserved for vetted, accredited Legal Metrology Officers. Everyday consumers have read-write access only to their own scanning telemetry and nutritional health assessments.
3. **Data Confidentiality and Trader Privacy**:
   While statutory declarations on retail packaging are public by law, internal officer audit remarks, draft notices of prosecution, geolocation heatmaps of retail inspection raids, and personal consumer scan patterns constitute sensitive data that must be protected with modern cryptographic ciphers at rest and in transit.
4. **Non-Repudiation and Attribution**:
   Every enforcement decision, notice dispatch, rule override, and officer verification must be permanently attributed to a specific verified user identifier, timestamped via synchronized NTP time sources, and recorded in an append-only audit ledger.
5. **High Availability and Resilience**:
   Enforcement officers operating in rural markets, state borders, and wholesale distribution centers require continuous, low-latency API availability. The authentication and scanning infrastructure must withstand denial-of-service attempts and credential stuffing attacks.

## 2. Authentication Architecture

### 2.1 Dual-Token Lifecycle Architecture
MetroScan implements an asynchronous token-based authentication system utilizing JSON Web Tokens (RFC 7519) with a dual-token scheme: a short-to-medium lifespan **Access Token** and a long-lifespan **Refresh Token**.

```
+---------------+              +-----------------------+              +----------------------+
|               |              |                       |              |                      |
| Client App    |              | MetroScan Auth API    |              | Redis Token Cache    |
| (React / App) |              | (FastAPI Application) |              | & PostgreSQL DB      |
+-------+-------+              +-----------+-----------+              +----------+-----------+
        |                                  |                                     |
        | 1. POST /api/auth/login          |                                     |
        |    (email, password)             |                                     |
        +--------------------------------->|                                     |
        |                                  | 2. Query User & Verify Bcrypt Hash  |
        |                                  |------------------------------------>|
        |                                  | 3. If Valid: Generate Access +      |
        |                                  |    Refresh Tokens (with unique jti) |
        |                                  | 4. Store Refresh JTI in Cache       |
        |                                  |------------------------------------>|
        | 5. Return: Access Token (JSON)   |                                     |
        |    + Set-Cookie: Refresh Token   |                                     |
        |<---------------------------------+                                     |
        |                                  |                                     |
        | [ Subsq. Inspection Requests ]   |                                     |
        | 6. GET /api/officer/dockets      |                                     |
        |    Header: Bearer <AccessToken>  |                                     |
        +--------------------------------->|                                     |
        |                                  | 7. Validate HS256 Sig, Expiry,      |
        |                                  |    RBAC Claims & JTI Denylist       |
        | 8. 200 OK (Inspection Data)     |<------------------------------------+
        |<---------------------------------+                                     |
        |                                  |                                     |
        | [ Token Expiration: 24h ]        |                                     |
        | 9. POST /api/auth/refresh        |                                     |
        |    Cookie: metros_refresh        |                                     |
        +--------------------------------->|                                     |
        |                                  | 10. Validate JTI, Check Revocation  |
        |                                  |------------------------------------>|
        |                                  | 11. Rotate Refresh Token (Revoke    |
        |                                  |     Old JTI, Issue New JTI Pair)    |
        | 12. Return New Token Pair        |<------------------------------------+
        |<---------------------------------+                                     |
```

#### Token Lifespan Parameters
- **Access Token Validity**: Exactly **24 hours** (86,400 seconds).
  - *Engineering Rationale*: Enforcement officers frequently conduct surprise retail audits and market sweeps in rural mandis, godowns, and wholesale logistics hubs where cellular connectivity is intermittent or unavailable. A standard 15-minute token would force disruptive session expiries during field operations. 24 hours provides operational continuity while limiting the credential exposure window.
- **Refresh Token Validity**: Exactly **7 days** (604,800 seconds).
  - *Engineering Rationale*: Provides seamless credential maintenance across multi-day enforcement assignments while mandating periodic credential re-validation.
- **Signature Algorithm**: **HMAC-SHA256 (HS256)** using a 256-bit cryptographically random secret key managed via high-entropy environment variables (`JWT_SECRET_KEY`). The architecture is forward-compatible with asymmetric **RS256** (RSA-SHA256 with 4096-bit keys) for multi-agency federal verification.

### 2.2 Exact JWT Payload Claims Specification

Every JWT issued by the MetroScan authentication service contains standardized claims defined in RFC 7519 along with system-specific regulatory enforcement claims.

#### Access Token Schema (JSON)
```json

  "sub": "4f8a3c21-9e20-4a89-b8d1-7c9b0e2d1f4a",
  "email": "inspector.verma@delhi.gov.in",

  "badge_number": "LM-DL-2024-8841",

```

#### Claims Definition Table

| Claim | Type | Description | Statutory / Technical Purpose | Nullable |
|---|---|---|---|---|
| `sub` | String (UUIDv4) | Subject Identifier | Unique persistent primary key of the user in the PostgreSQL `users` table. | No |
| `email` | String | User Email Address | Canonical email used for notifications, audit indexing, and official communications. | No |
| `role` | String (Enum) | Authorization Tier | Must be exactly one of: `consumer`, `officer`, `admin`. Governs endpoint RBAC guards. | No |
| `badge_number` | String | Government Inspector Badge ID | Official departmental identification number issued by the Legal Metrology Controller. | Yes (Null for `consumer`) |

| `iat` | Integer (Epoch) | Issued At Timestamp | UNIX epoch timestamp marking token issuance for clock skew and age validation. | No |
| `exp` | Integer (Epoch) | Expiration Timestamp | UNIX epoch timestamp marking expiry (`iat + 86400` for access tokens). | No |
| `jti` | String (UUIDv4) | JWT Unique ID | Cryptographically unique token identifier used for single-use token rotation and Redis denylisting. | No |

### 2.3 Refresh Token Schema and Rotation Policy
Refresh tokens contain a restricted payload containing only `sub`, `jti`, `iat`, and `exp`.

```json
{
  "sub": "4f8a3c21-9e20-4a89-b8d1-7c9b0e2d1f4a",
  "jti": "9a8b7c6d-5e4f-3a2b-1c0d-e9f8a7b6c5d4",
  "iat": 1789036800,
  "exp": 1789641600
}
```

#### Strict Refresh Token Rotation (RTR) Mechanism:
1. Refresh tokens are strictly **single-use**.
2. When `/api/auth/refresh` is invoked, the incoming `jti` is checked against the Redis token registry.
3. If the `jti` is valid and active, the backend immediately marks the incoming `jti` as consumed/revoked in Redis, generates a completely fresh Access Token and Refresh Token pair with new `jti` values, and returns them to the client.
4. **Replay Attack Detection**: If a consumed `jti` is presented a second time (indicating that the token was intercepted by an adversary), the authentication service triggers an immediate security alert:
   - All active tokens associated with that `sub` are instantly invalidated in Redis.
   - The user account is temporarily locked.
   - A critical security warning is written to the audit log.

### 2.4 Token Storage and Transport Security Recommendations

The system mandates distinct storage and transport strategies depending on client runtime:

#### Web Browser Client (React 19 SPA)
1. **Refresh Token Transport**:
   - Transmitted exclusively via an `HttpOnly`, `Secure`, `SameSite=Strict` cookie named `metros_refresh`.
   - The cookie path is strictly scoped to `/api/auth/refresh` to prevent leakage to general API endpoints.
   - The `HttpOnly` flag completely prevents JavaScript access, rendering cross-site scripting (XSS) credential exfiltration impossible.
2. **Access Token Transport**:
   - Stored strictly in application memory (React state / auth context closure).
   - Injected into outbound API calls via the standard HTTP header:  
     `Authorization: Bearer <access_token>`
   - *Never stored in `localStorage` or `sessionStorage`*, eliminating token harvesting via third-party script vulnerabilities or DOM injection.
3. **Cross-Site Request Forgery (CSRF) Mitigation**:
   - For state-modifying requests that rely on cookies (such as token refresh), the API enforces custom header validation: clients must supply `X-Requested-With: MetroScanClient`. Browser security prevents unauthorized cross-origin requests from injecting custom headers without explicit CORS pre-flight authorization.

#### Mobile / Field Client (Android / Flutter Tablet App)
- Both access and refresh tokens must be stored in hardware-backed secure storage:
  - **Android**: `EncryptedSharedPreferences` backed by the Android KeyStore System (hardware Keymaster / StrongBox).
  - **iOS**: Keychain Services with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`.

### 2.5 Password Security and Hashing Policy
User passwords represent the root authentication credential and are protected using adaptive key-derivation algorithms:

1. **Hashing Algorithm**: **Bcrypt** (`bcrypt` with OpenBSD `$2b$` prefix).
2. **Work Factor (Cost)**: **Minimum 12 rounds** (`cost=12`).
   - Generates 4,096 iterations of key expansion.
   - Requires approximately 280 to 350 milliseconds of CPU execution time per hash on modern server processors.
   - Guarantees high resistance to parallel GPU/ASIC dictionary attacks.
3. **Salt Generation**: Automatically generates a unique, cryptographically secure 128-bit pseudorandom salt for every password record using `os.urandom(16)`.
4. **Timing Attack Protection**: Password verification utilizes constant-time string comparison (`hmac.compare_digest` or `bcrypt.checkpw`) to prevent execution-timing side-channel attacks.
5. **Password Complexity Requirements**:
   Every password accepted during registration or credential rotation must satisfy all of the following rules:
   - Minimum length: **8 characters** (Enforcement officers are advised to use 12+ characters).
   - At least one uppercase alphabetic character (`[A-Z]`).
   - At least one lowercase alphabetic character (`[a-z]`).
   - At least one numerical digit (`[0-9]`).
   - At least one special ASCII character (`[!@#$%^&*()_+\-=[\]{};':"\\|,.<>/?]`).
   - Must not contain the user email prefix or obvious dictionary words (`password`, `admin`, `metroscan`).

## 3. Role-Based Access Control (RBAC) Matrix

### 3.1 Role Hierarchy and Definitions
MetroScan defines three strictly segregated user roles:

```
                  +--------------------------+
                  |          ADMIN           |
                  | Central Legal Metrology  |
                  | System Administrator     |
                  +------------+-------------+
                               |
                               | (Supervises & Vets)
                               v
                  +--------------------------+
                  |         OFFICER          |
                  | Legal Metrology Inspector|
                  | Enforcement Official     |
                  +------------+-------------+

                               v
                  +--------------------------+
                  |         CONSUMER         |

                  | Retail Shopper           |
                  +--------------------------+
```

1. **`consumer`**:
   Default citizen role. Self-registered without administrative vetting. Permissions focus on product verification, statutory label discovery, nutritional health evaluation (ICMR-NIN 2024 standards), and submission of consumer grievance reports.

   Accredited field inspector or enforcement officer appointed under Section 13 of the Legal Metrology Act, 2009. Access requires administrative vetting of physical government credentials. Permissions include dimensional font height analysis, non-compliant packaging seizure workflows, formal show-cause notice creation, FORM LM-INSP-2011 docket compilation, and district enforcement analytics.
3. **`admin`**:
   Central Directorate system administrator (Department of Consumer Affairs, Legal Metrology Division). Responsible for verifying officer credentials, granting enforcement privileges, monitoring tamper audit ledgers, maintaining statutory rule thresholds, and system health governance.

### 3.3 Enforcement Officer Onboarding and Vetting Workflow

Because officers possess state statutory powers to issue formal notices of prosecution, officer accounts cannot be self-activated. The system enforces a multi-step verification state machine:

```
  +------------------+
  | Officer Signup   |  (Provides Badge No, Zone, Official Email, ID Card Image)
  +--------+---------+
           |
           v
  +--------------------------------+
  | Status: PENDING_VERIFICATION   |  (Account exists; role is 'officer'; is_verified=False)
  | Can ONLY access consumer APIs  |
  +--------+-----------------------+
           |
           |-- Admin reviews physical badge in State Metrology Cadre Database
           |-- Admin inspects official ID scan & contact coordinates
           |
     +-----+--------------------------+
     |                                |
     v (Approved)                     v (Rejected)
  +-------------------------+      +-------------------------+
  | Status: ACTIVE          |      | Status: REJECTED        |
  | is_verified = True      |      | is_verified = False     |
  | Full Officer Privileges |      | Notification dispatched |
  +------------+------------+      +-------------------------+
               |
               v (Transfer / Suspension / Misconduct)
  +-------------------------+
  | Status: SUSPENDED       |
  | Immediate JTI Denylist  |
  | Zero API Access         |
  +-------------------------+
```

#### Detailed Workflow Protocol:
1. **Self-Registration Phase**:
   - The prospective officer submits the registration payload containing: Full Name, Official Government Email (`.gov.in`, `.nic.in`, or designated state police/metrology domain), Password, Official Government Badge Number (`badge_number`), and Assigned Enforcement Zone (`zone`).
   - The user record is created with `role = "officer"`, `is_verified = False`, and `is_active = True`.
   - The officer cannot access any `/api/officer/*` endpoints. Attempted access results in an HTTP `403 Forbidden` with the error code `OFFICER_NOT_VERIFIED`.
2. **Administrative Vetting Phase**:
   - Central Administrators view the pending verification queue at `/api/admin/officers/pending`.
   - The administrator verifies the submitted badge number against the official cadre roll of the State Legal Metrology Department.
   - The administrator inspects jurisdiction zone mapping to confirm operational posting.
3. **Approval Execution**:
   - The administrator calls `/api/admin/officers/{id}/verify`.
   - The backend executes an atomic database transaction:
     - Sets `is_verified = True`.
     - Updates `verified_by = admin_user_id` and `verified_at = CURRENT_TIMESTAMP`.
     - Writes an immutable event to `security_audit_logs` capturing Admin ID, Officer ID, Badge Number, and client IP address.
     - Dispatches an automated verification notification email to the officer.
4. **Revocation and Suspension**:
   - If an officer is transferred, suspended, or faces departmental inquiry, an administrator calls `/api/admin/officers/{id}/suspend`.
   - The backend sets `is_active = False` and broadcasts a revocation command to Redis, immediately blacklisting all active JTIs issued to that officer. Subsequent requests with existing access tokens are rejected instantly.

## 4. Evidence Chain of Custody & Image Integrity

### 4.1 Evidentiary Admissibility under Bharatiya Sakshya Adhiniyam, 2023 (BSA)
Section 63 of the Bharatiya Sakshya Adhiniyam, 2023 governs the admissibility of electronic records in Indian courts (replacing Section 65B of the repealed Indian Evidence Act, 1872). To ensure that digital inspection dockets and extracted packaging photos generated by MetroScan are admissible as uncompromised primary legal evidence, the system implements technical controls directly mapped to BSA Section 63 statutory conditions:

1. **Lawful Control and Ordinary Course of Activity (BSA Section 63(2)(a))**:
   The system records that the electronic device and software were operated by an accredited enforcement officer acting within their lawful official duties at the time of inspection.
2. **Continuous System Operational Integrity (BSA Section 63(2)(b))**:
   System diagnostic logs prove that the computer vision and optical recognition systems were operating properly throughout the period, without malfunctions capable of corrupting digital artifacts.
3. **Reproduction Fidelity (BSA Section 63(2)(c))**:
   Digital exhibits generated for the court docket are identical reproductions of the data fed into the device during the retail inspection.
4. **Statutory Electronic Record Certificate (BSA Section 63(4))**:
   Every inspection docket automatically compiles an accompanying **Schedule Certificate of Electronic Evidence** containing:
   - SHA-256 cryptographic digest of the primary packaging image.
   - Complete hardware serial/UUID and client IP address of the scanning device.
   - Exact UTC and IST timestamp synchronized with National Physical Laboratory (NPL) reference clocks.
   - Name, badge number, and digital signature placeholder of the seizing officer.

### 4.2 Ingest Cryptographic Verification & SHA-256 Hashing Pipeline

To prevent any allegation that an image was altered, manipulated, or synthesized after submission, MetroScan executes hashing at the earliest possible network stage:

```
[ Packaging Image Stream ]
            |
            v
+-------------------------------------------------------------------+
| 1. FastAPI Ingest Buffer (In-Memory Streaming Chunk Processor)    |
|    - Computes SHA-256 Hash ON-THE-FLY before writing to disk      |
|    - Checks file size <= 10MB (10,485,760 bytes)                  |
|    - Verifies True Binary Magic Bytes (JPEG/PNG/WEBP)             |
+---------------------------------+---------------------------------+
                                  |
                                  +--> Computed SHA-256 Digest
                                  |    (e.g., e3b0c44298fc1c149af...)
                                  v
+-------------------------------------------------------------------+
| 2. Atomic Relational Commit (`inspection_evidence_artifacts`)      |
|    - Stores: original_sha256, uploader_id, captured_at, zone_id   |
|    - Sets: is_locked = True (Append-Only)                         |
+---------------------------------+---------------------------------+
                                  |
            +---------------------+---------------------+
            |                                           |
            v                                           v
+-----------------------------+             +-------------------------------+
| Raw Evidence Vault          |             | Working Processing Engine     |
| Path: /vault/raw/{sha256}   |             | - Normalization & Dewarping   |
| - Read-Only (POSIX 0400)    |             | - OCR & Bounding Box Overlays |
| - WORM Compliant Storage    |             | - Rule 7 Font Height Metrics  |
| - Zero EXIF Stripping       |             | - High-Contrast Watermarking  |
| - Retained for Court Record |             +-------------------------------+
+-----------------------------+
```

#### Ingestion Code Implementation Standard
```python
import hashlib
from fastapi import UploadFile, HTTPException, status

async def process_and_hash_evidence_stream(file: UploadFile) -> tuple[bytes, str]:
    """
    Reads uploaded file stream in 64KB memory chunks, computing SHA-256
    hash synchronously before any persistence. Enforces strict 10MB limit.
    """
    MAX_FILE_SIZE = 10 * 1024 * 1024  # Exactly 10 Megabytes
    hasher = hashlib.sha256()
    byte_chunks = []
    total_bytes = 0

    while chunk := await file.read(65536):  # 64 KB chunks
        total_bytes += len(chunk)
        if total_bytes > MAX_FILE_SIZE:
            raise HTTPException(
                status_code=status.HTTP_413_REQUEST_ENTITY_TOO_LARGE,
                detail="Uploaded packaging image exceeds maximum allowable limit of 10MB."
            )
        hasher.update(chunk)
        byte_chunks.append(chunk)

    raw_bytes = b"".join(byte_chunks)
    sha256_digest = hasher.hexdigest()
    return raw_bytes, sha256_digest
```

### 4.3 Dual-Vault Image Storage Architecture

MetroScan strictly isolates **Raw Legal Evidence** from **Working Computer Vision Artifacts**:

1. **Vault 1: Immutable Raw Evidence Vault**:
   - Dedicated secure directory or S3 bucket with Object Lock enabled (Write Once, Read Many - WORM).
   - Filename is strictly the 64-character hexadecimal SHA-256 digest (`/evidence/raw/{sha256}.bin`).
   - File permissions are set to POSIX `0400` (read-only by the service owner; zero write/execute permissions).
   - Original EXIF metadata, camera device serials, and uncompressed pixel buffers are preserved without alteration.
   - Used exclusively for court verification challenges: an endpoint `/api/officer/evidence/{id}/verify` recomputes the SHA-256 hash in real time and asserts equality against the stored database value.
2. **Vault 2: Working & Derivative Artifact Storage**:
   - Stores scaled images, optical bounding box annotations, contrast segmentation masks, and watermarked docket attachments.
   - Metadata is sanitized to eliminate external leaks.
   - Public consumer viewing queries consume derivative artifacts, ensuring the raw evidence vault remains air-gapped from public network paths.

### 4.4 Forensic Watermarking Architecture
When inspection images are compiled into statutory dockets (FORM LM-INSP-2011) or exported for administrative show-cause notices, the system burns an indelible forensic watermark into the image banner.

#### Watermark Visual Layout
```
+----------------------------------------------------------------------------------------------------+
|                                                                                                    |
|                                     PACKAGING EVIDENCE IMAGE                                       |
|                                                                                                    |
+----------------------------------------------------------------------------------------------------+
| METROSCAN STATUTORY EVIDENCE | DOCKET: LM-DL-2026-00481 | SHA256: 7f83b165...4b2e                  |
| OFFICER: INSP. S. VERMA (BADGE: LM-DL-2024-8841) | ZONE: DL-NORTH-01                               |
| TIMESTAMP: 2026-09-10 14:32:08 IST (10:02:08 UTC)                                                  |
| LOCATION: LAT 28.613938 N, LON 77.209021 E (ACCURACY: +/- 4.2M)                                    |
+----------------------------------------------------------------------------------------------------+
```

#### Forensic Banner Specifications:
- **Placement**: Fixed banner at the bottom margin of the packaging image, spanning 100% width with a calculated height of 8% of image height (minimum 120 pixels).
- **Background**: Solid opaque black (`#000000`) or high-opacity charcoal (`rgba(15, 23, 42, 0.95)`), guaranteeing complete legibility irrespective of packaging colors.
- **Typography**: High-legibility monospaced typeface (e.g. Courier Prime or Roboto Mono), rendered in stark white (`#FFFFFF`) with yellow accent highlights (`#FACC15`) for docket numbers.
- **Mandatory Watermark Metadata Fields**:
  1. System Identifier: `METROSCAN STATUTORY EVIDENCE (LEGAL METROLOGY ACT, 2009)`
  2. Inspection Docket Number: Unique alphanumeric case ID (`LM-{ZONE}-{YEAR}-{SEQUENCE}`).
  3. SHA-256 Digest Truncation: Leading 8 and trailing 8 hex characters of raw image digest.
  4. Seizing Officer Credentials: Full Name and Departmental Badge Number.
  5. Dual Timestamp: Indian Standard Time (IST) and Coordinated Universal Time (UTC) down to the second.

## 5. Application Security & Defenses

### 5.1 Strict File Upload Hardening & Magic Byte Validation
Adversaries may attempt to upload disguised web shells, polyglot binaries, or cross-site scripting vectors disguised as product photos. MetroScan rejects file classification based on the `Content-Type` HTTP header or client-supplied file extensions, enforcing deep binary signature inspection.

#### Binary Magic Byte Signatures

| Image Format | Offset | Magic Byte Sequence (Hexadecimal) | Validation Standard |
|---|---|---|---|
| **JPEG / JPG** | `0` | `FF D8 FF` | Standard Joint Photographic Experts Group header |
| **PNG** | `0` | `89 50 4E 47 0D 0A 1A 0A` | Standard Portable Network Graphics 8-byte signature |
| **WEBP** | `0` and `8` | Bytes 0-3: `52 49 46 46` (`RIFF`), Bytes 8-11: `57 45 42 50` (`WEBP`) | Google WebP Resource Interchange File Format |

#### Prohibited MIME and File Formats:
- **SVG (`image/svg+xml`)**: **Strictly Prohibited**. SVG files permit XML entities and `<script>` execution tags, presenting an extreme stored XSS risk.
- **TIFF / BMP**: **Rejected**. Inefficient compression and potential buffer overflow vectors in legacy decoding libraries.
- **Executables / Archives**: Any file containing `MZ` (`4D 5A`), `PK\x03\x04`, or `\x7FELF` headers is immediately rejected and flagged as a security violation.

#### Validation Implementation Architecture
```python
import magic
from fastapi import HTTPException, status

ALLOWED_MIME_TYPES = {
    "image/jpeg": [b"\xff\xd8\xff"],
    "image/png": [b"\x89PNG\r\n\x1a\n"],
    "image/webp": [b"RIFF"]  # further inspected for WEBP at byte 8
}

def validate_image_binary(raw_bytes: bytes) -> str:
    """
    Validates binary header magic bytes against allowed image formats.
    Returns normalized MIME string or raises HTTP 400.
    """
    if len(raw_bytes) < 16:
        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST,
            detail="File corruption detected: payload too small to determine binary signature."
        )

    # Magic byte signature matching
    if raw_bytes.startswith(b"\xff\xd8\xff"):
        return "image/jpeg"
    elif raw_bytes.startswith(b"\x89PNG\r\n\x1a\n"):
        return "image/png"
    elif raw_bytes.startswith(b"RIFF") and raw_bytes[8:12] == b"WEBP":
        return "image/webp"

    # Secondary validation using libmagic
    mime_detector = magic.Magic(mime=True)
    detected_mime = mime_detector.from_buffer(raw_bytes[:2048])
    if detected_mime not in ALLOWED_MIME_TYPES:
        raise HTTPException(
            status_code=status.HTTP_415_UNSUPPORTED_MEDIA_TYPE,
            detail=f"Security rejection: Invalid binary signature '{detected_mime}'. Only JPEG, PNG, and WEBP permitted."
        )
    return detected_mime
```

### 5.2 Token Bucket Rate Limiting Architecture
To safeguard scanning APIs against distributed denial of service, resource exhaustion, and automated data scraping, MetroScan implements the **Token Bucket Algorithm** backed by Redis.

#### Rate Limiting Quota Configuration

| Endpoint Category | Route Pattern | Target Principal | Sustained Rate | Burst Limit | Window / Period | Action on Exceeded |
|---|---|---|---|---|---|---|
| **Public Auth** | `/api/auth/login` | IP Address | 5 requests | 10 requests | 5 minutes | HTTP 429 + 15 min lock |
| **Consumer Scans** | `/api/scan/*` | Authenticated User | 20 scans | 25 scans | 1 minute | HTTP 429 (Retry-After) |
| **Consumer Scans** | `/api/scan/*` | Anonymous IP | 10 scans | 12 scans | 1 minute | HTTP 429 (Retry-After) |
| **Officer Scans** | `/api/scan/*` | Verified Officer | 60 scans | 80 scans | 1 minute | High-throughput sweep allowance |
| **Docket Export** | `/api/officer/reports/*`| Verified Officer | 10 exports | 15 exports | 1 minute | Prevents PDF worker saturation |
| **Admin Operations**| `/api/admin/*` | Verified Admin | 100 requests | 150 requests | 1 minute | Unrestricted administrative quota |

#### Rate Limit Response Headers (RFC 6585)
When a client invokes any rate-controlled route, the server provides real-time quota telemetry in standard HTTP headers:
- `X-RateLimit-Limit`: Maximum tokens permitted in the operational window.
- `X-RateLimit-Remaining`: Tokens currently available in the caller's bucket.
- `X-RateLimit-Reset`: UNIX epoch seconds until the bucket is completely replenished.

When quota is exhausted, the API immediately responds with HTTP `429 Too Many Requests`:
```json
{
  "error": "RATE_LIMIT_EXCEEDED",
  "message": "Scanning quota exhausted. Allowed 20 scans per minute.",
  "retry_after_seconds": 24
}
```

### 5.3 Injection Defenses & Input Sanitization

#### SQL Injection (SQLi) Defense
MetroScan utilizes **SQLAlchemy 2.0 ORM** with absolute prohibition of raw string concatenation or unsanitized SQL text templates.
- All database queries are compiled into parameterized prepared statements where user parameters are transferred out-of-band via database driver binary protocols.
- Automated static analysis (using `bandit` and `semgrep` in CI/CD pipelines) blocks any merge containing `.execute(f"SELECT ...")` or raw SQL formatting.

```python

stmt = select(InspectionDocket).where(
    InspectionDocket.zone_code == bind_zone,
    InspectionDocket.is_active == True
).order_by(InspectionDocket.created_at.desc())
result = await db_session.execute(stmt)

# PROHIBITED & LINT-BLOCKED: Raw SQL String Formatting
# cursor.execute(f"SELECT * FROM dockets WHERE zone = '{user_input}'")  # VIOLATION
```

#### Cross-Site Scripting (XSS) & Content Security Defense
1. **Frontend JSX Escaping**:
   React 19 treats all values embedded in JSX bindings `{value}` as untrusted strings, automatically escaping HTML entities (`&`, `<`, `>`, `"`, `'`) before DOM insertion.
2. **Pydantic Validation and Bleach Sanitization**:
   All text fields accepted from API requests (such as merchant names, officer inspection notes, and product descriptions) are parsed through Pydantic v2 validators that strip HTML tags and control characters.
3. **HTTP Security Response Headers**:
   FastAPI middleware injects strict browser security headers on all responses:
   - `Content-Security-Policy`: `default-src 'self'; img-src 'self' data: blob:; script-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none';`
   - `X-Content-Type-Options`: `nosniff` (prevents MIME-type sniffing).
   - `X-Frame-Options`: `DENY` (prevents clickjacking attacks).
   - `Strict-Transport-Security`: `max-age=63072000; includeSubDomains; preload` (enforces HSTS for 2 years).
   - `Referrer-Policy`: `strict-origin-when-cross-origin`.

### 6.1 FastAPI RBAC Dependency Implementation

The following production-ready FastAPI security module demonstrates the exact dependency injection pattern used to guard endpoints across MetroScan:

```python
# File reference: backend/routers/deps.py

from typing import List, Optional
from datetime import datetime, timezone
import jwt
from fastapi import Depends, HTTPException, Security, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
from pydantic import BaseModel, ValidationError

# Configuration constants
JWT_SECRET_KEY = "CHANGE_IN_PRODUCTION_ENV_KEEP_HIGH_ENTROPY_256BIT"
JWT_ALGORITHM = "HS256"

security_bearer = HTTPBearer(auto_error=True)

class TokenPayload(BaseModel):
    sub: str
    email: str
    role: str
    badge_number: Optional[str] = None
    zone: Optional[str] = None
    iat: int
    exp: int
    jti: str

class AuthenticatedUser(BaseModel):
    id: str
    email: str
    role: str
    badge_number: Optional[str] = None
    zone: Optional[str] = None
    is_verified: bool

async def get_current_user(
    credentials: HTTPAuthorizationCredentials = Security(security_bearer)
) -> AuthenticatedUser:
    """
    Decodes and validates JWT bearer token from Authorization header.
    Validates cryptographic signature, expiration, and required claims.
    """
    token = credentials.credentials
    try:
        payload_dict = jwt.decode(
            token,
            JWT_SECRET_KEY,
            algorithms=[JWT_ALGORITHM]
        )
        token_data = TokenPayload(**payload_dict)
    except jwt.ExpiredSignatureError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Session expired: Access token has expired. Please refresh your session.",
            headers={"WWW-Authenticate": "Bearer"}
        )
    except (jwt.PyJWTError, ValidationError):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Authentication failed: Malformed or invalid credential token.",
            headers={"WWW-Authenticate": "Bearer"}
        )

    return AuthenticatedUser(
        id=token_data.sub,
        email=token_data.email,
        role=token_data.role,
        badge_number=token_data.badge_number,
        zone=token_data.zone,
        is_verified=True if token_data.role == "officer" and token_data.badge_number else False
    )

class RoleChecker:
    """
    RBAC dependency factory validating that caller possesses one of
    the allowable role designations.
    """
    def __init__(self, allowed_roles: List[str]):
        self.allowed_roles = allowed_roles

    def __call__(self, user: AuthenticatedUser = Depends(get_current_user)) -> AuthenticatedUser:
        if user.role not in self.allowed_roles:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"Access denied: Operation requires one of the following roles: {self.allowed_roles}."
            )
        if user.role == "officer" and not user.badge_number:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Access restricted: Officer account pending departmental badge verification."
            )
        return user

# Pre-defined dependency guards
require_consumer = RoleChecker(["consumer", "officer", "admin"])
require_officer = RoleChecker(["officer", "admin"])
require_admin = RoleChecker(["admin"])
```

### 6.2 Forensic Watermarking Utility Implementation

```python
# File reference: backend/services/watermark_service.py

import os
from datetime import datetime, timezone, timedelta
from PIL import Image, ImageDraw, ImageFont

def apply_forensic_watermark(
    image_path: str,
    output_path: str,
    docket_id: str,
    officer_badge: str,
    officer_name: str,
    zone: str,
    sha256_hash: str,
    latitude: float = None,
    longitude: float = None,
    accuracy_m: float = None
) -> str:
    """
    Applies an indelible, high-contrast statutory forensic watermark banner
    to the bottom of the packaging evidence image for court admissibility.
    """
    with Image.open(image_path) as base_img:
        base_img = base_img.convert("RGB")
        width, height = base_img.size

        # Compute dynamic banner height (minimum 130px or 8% of image height)
        banner_height = max(130, int(height * 0.08))
        new_height = height + banner_height

        # Create canvas with extended bottom banner
        canvas = Image.new("RGB", (width, new_height), color=(15, 23, 42))  # Slate 900
        canvas.paste(base_img, (0, 0))

        draw = ImageDraw.Draw(canvas)

        # Timestamps
        utc_now = datetime.now(timezone.utc)
        ist_now = utc_now + timedelta(hours=5, minutes=30)
        time_str_ist = ist_now.strftime("%Y-%m-%d %H:%M:%S IST")
        time_str_utc = utc_now.strftime("%Y-%m-%d %H:%M:%S UTC")

        # Geolocation string
        if latitude is not None and longitude is not None:
            acc_str = f" (+/- {accuracy_m:.1f}m)" if accuracy_m else ""
            geo_str = f"LAT {latitude:.6f} N, LON {longitude:.6f} E{acc_str}"
        else:
            geo_str = "GEOLOCATION: NOT AVAILABLE (DESKTOP INGEST)"

        truncated_hash = f"{sha256_hash[:8]}...{sha256_hash[-8:]}"

        # Text Lines
        line1 = f"METROSCAN EVIDENCE ARCHIVE | DOCKET: {docket_id} | RAW SHA256: {truncated_hash}"
        line2 = f"OFFICER: {officer_name.upper()} (BADGE: {officer_badge}) | ZONE: {zone}"
        line3 = f"TIMESTAMP: {time_str_ist} ({time_str_utc})"
        line4 = f"COORDINATES: {geo_str}"

        # Draw decorative top border line for the banner
        draw.line([(0, height), (width, height)], fill=(250, 204, 21), width=3)  # Accent Yellow

        # Render text lines
        font_size = max(14, int(banner_height / 6.5))
        try:
            font = ImageFont.truetype("DejaVuSans-Bold.ttf", font_size)
        except IOError:
            font = ImageFont.load_default()

        y_offset = height + 10
        spacing = int(banner_height / 4.8)

        draw.text((15, y_offset), line1, fill=(250, 204, 21), font=font)
        draw.text((15, y_offset + spacing), line2, fill=(255, 255, 255), font=font)
        draw.text((15, y_offset + spacing * 2), line3, fill=(226, 232, 240), font=font)
        draw.text((15, y_offset + spacing * 3), line4, fill=(148, 163, 184), font=font)

        canvas.save(output_path, "JPEG", quality=95)
        return output_path
```
